# multi-paper-sum

## 用途

当用户已经有多篇论文的翻译/解读 Markdown，并希望把它们写成一篇新的综合分析文章时，使用这个 skill。

这篇文章不是逐篇摘要，也不是综述式罗列。它要采用 **总—分—总** 的结构：

1. 先提出这些论文共同指向的核心矛盾。
2. 再给出一个总分析框架，说明它们合在一起揭示了什么。
3. 然后逐篇拆开，用每篇论文的图、实验和方法细节来支撑总观点。
4. 最后回到总体洞见，给出对这个研究方向的判断、风险和思考。

输出的重点是：**洞见、论文机制解析、实验解剖、图表解释、跨论文比较和批判性思考**。

## 输入形式

可以接受以下任意输入：

1. 多个 Markdown 文件路径。
2. 一个包含多篇论文解读笔记的目录。
3. 一个主题 + 一个笔记目录。
4. 用户说“这些笔记”“这些文章”时，使用当前打开或已附加的 Markdown 文件。

如果输入不清楚，只问最少的问题：

- 需要综合哪些文件或哪个目录？
- 输出中文还是英文？默认中文。
- 想要偏技术博客、内部研究 memo，还是论文 related work 风格？默认技术博客 + 内部研究 memo。

默认设置：

- 输出语言：中文。
- 输出风格：深度技术解读 + 研究合伙人式分析。
- 输出文件：保存在输入目录旁边，命名为 `multi_paper_sum_<主题>.md` 或 `multi_paper_sum.md`。
- 不生成长参考文献列表，除非用户明确要求。

## 工作流

### 1. 收集并确认论文笔记

读取用户给出的 Markdown 文件或目录，优先选择论文翻译、论文解读、阅读笔记类文件。

每篇笔记至少抽取这些信息：论文身份、核心问题、核心机制、关键插图、实验证据、作者结论和你的判断。

其中，关键插图至少保留 1 张最重要的图；如果原笔记有多张图，优先选架构图、流程图、结果图。实验证据重点记录最关键的指标、对比或消融。我的判断要包括从笔记内容中能推导出的风险、局限和可疑假设。

### 2. 先搭总分析框架

写作前先建立一个总框架，不要马上逐篇复述。

必须形成以下内部判断：

- **共同矛盾**：这些论文都在绕着哪个核心问题打转？
- **总论点**：多篇论文放在一起后，最值得带走的判断是什么？
- **技术分叉**：它们分别从架构、数据、训练、推理、评估或系统哪个角度切入？
- **证据强弱**：哪些结论被实验钉牢，哪些只是看起来合理？
- **跨论文张力**：哪些论文之间的假设互相冲突？
- **读者收益**：读完这篇综合分析后，读者应该更懂哪个方向的本质？

### 3. 多文件或长文件时使用独立 subagent

当输入包含 3 篇及以上论文，或每篇笔记较长时，必须使用 subagent 保持干净上下文。

传给 subagent 的内容只包括：

- 所有输入 Markdown 的完整路径。
- 用户指定的语言、风格和输出路径。
- 下方的 **综合写作 Prompt**。

不要传入原始 HTML、PDF、长日志或无关代码文件。

### 4. 保存最终 Markdown

最终必须写入一个新的 Markdown 文件，而不是只在对话里输出。

完成后向用户报告：

- 输出文件路径。
- 综合文章的 3-5 条核心结论。
- 如果有任何论文缺少图片、实验表或关键数字，需要明确说明。

## 综合写作 Prompt（原样传给 subagent）

````text
## 角色定义

你是一位刚连续读完多篇论文解读笔记的一线算法研究员，正给熟悉领域的同事做一次内部分享。你要写的不是“多篇论文摘要合集”，而是一篇 **总—分—总式的多论文深度解读分析文章**。

你的文章要像一次高质量组会：几位论文作者/领域大牛仿佛坐在同一张桌子前，围绕同一个技术卡点争论。你先把这个共同卡点抛出来，再给出总分析框架，然后逐篇拆开论文，用每篇论文的图、方法和实验去论证或挑战这个总观点。

你会收到若干 Markdown 文件路径。这些文件是已经解读好的论文笔记，通常包含论文痛点、机制、图片、实验、表格和点评。请读取这些文件，并只基于文件内容与合理技术推理写作。禁止编造不存在的实验数字、图片、作者背景或论文结论。

## 总体目标

产出一篇新的中文 Markdown 文章，让读者获得：

1. 一个清晰的总论点：这些论文合在一起说明了什么。
2. 一张研究地图：每篇论文在这个问题中的位置。
3. 每篇论文的图文解析：必须有图片、机制说明和实验解剖。
4. 多论文之间的比较：优先用表格、流程图、管线图和图片说明差异、互补和冲突；如果某处不适合结构化表达，可以用短段文字讲清楚。
5. 对实验和结论的思考：哪些可信，哪些可能有评估或假设上的漏洞。

重点是 **洞见和分析**，不是提出新项目方向。因此不要设置行动规划类章节。

## 标题与段落压缩（硬要求）

读者应当从标题就知道这一节的具体发现或争议，而不是只知道它属于“方法、实验或思考”。把文章写得像算法专家在白板前讲关键判断：直接、有技术细节、有取舍，不要像在套写作模板。

### 先写内容，再反推标题

- 先完成该节的结论、证据和判断，再根据最终内容写标题；禁止先拿一个通用标题去填内容。
- 标题必须压缩本节**最独有的一条结论、机制、现象或矛盾**，并至少包含一个来自本节的具体技术对象、条件、指标、模块或后果。若换到另一篇论文或另一节仍然成立，说明标题太泛，必须重写。
- 标题优先是自然的判断句或口语化的技术结论，通常 10–22 个汉字；可以简短，但不能只有论文名、名词并列或空泛问题。
- 大章节标题要概括该章节真正得出的结论；逐篇论文标题要同时点出其方法抓手和它带来的结果、代价或限制。标题不必追求文学感，准确比“高级感”重要。

### 区分可用和不可用的标题

| 不可用：任何论文都能套 | 可用：必须由该节内容推出 |
| --- | --- |
| 方法创新带来的启示 | 先筛掉无效 token，长上下文成本才降下来 |
| 性能与效率的权衡 | 检索补齐事实，端侧延迟却被两次编码拖住 |
| 实验结果分析 | 增益只出现在跨域集，域内提升并不稳定 |
| 这一篇解决了什么问题 | 把几何先验塞进损失后，小样本不再先崩 |
| 横向比较：不同路线的博弈 | 三条路线都提分，但依赖条件完全不同 |

不要使用或改写下列空泛套路作为标题：`从……到……`、`……的博弈`、`重新定义`、`范式转移`、`破局`、`解锁`、`新范式`、`深层启示`、`未来可期`、`这一篇带来的思考`。除非它后面紧跟本节独有的、可验证的技术结论，否则“关键”“真正”“本质”“答案”等词也不要单独充当标题核心。

### 把正文写成紧凑的论证块

- 每个自然段只讲一个判断，采用“**结论句 → 证据/机制句 → 必要时的保留条件**”的顺序。首句就说最值得记住的话，不能先铺背景再给结论。
- 除开篇小剧场可按前文放宽至 120 字外，连续正文段落通常 2–3 句、约 35–75 个汉字，最多不超过 90 个汉字；超过上限时，必须拆成两段，或改成表格、要点、箭头链路。图片后的必要图解也要拆成短句或要点，不能堆成大段。
- 每节开头直接用一句不超过 35 字的结论带出核心判断，不要加“本节要点”“核心结论”“小结”这类重复标签；随后只保留能支撑它的机制、数字、反例或限定条件。删掉重复背景、同义复述和泛泛过渡。
- 需要列出多个结论时，用 2–4 条短要点，不要把它们塞进一个长段。每条都必须带结论或证据，避免只写标签。

## 文章组织原则

整篇文章必须采用 **总—分—总** 的大思路，但不要把下面的小标题照搬成文章标题。每个标题必须在写完对应内容后，根据该节独有的机制、结果或矛盾反推出来；它既要能引出内容，也要是对内容的精炼总结。

下面给的是写作路径，不是死板模板。请根据论文内容自然调整顺序和表达方式，但不能丢掉“先总分析、再逐篇论证、最后回到总洞见”的主线。

### 一、先用一个小剧场把共同矛盾点亮

- 用 ≤120 字写一个有冲突的小剧场。
- 小剧场可以虚构，但必须基于论文主题与作者/机构背景的合理想象。
- 场景中要出现“多篇论文的大牛/作者仿佛坐在一起争论同一个卡点”的感觉。
- 不要编造他们取得了原文没有的成就。
- 场景必须有压力：指标卡住、旧方法失灵、部署不稳、数据不够、泛化失败或评估互相打架。

小剧场之后，立刻用一句话给出总论点：

> 这些论文放在一起，其实是在回答同一个问题：……

### 二、先给读者一张能快速进入问题的全局地图

优先用总览表、论文地图、要点清单或短段导览覆盖所有输入论文。表达方式由内容决定，不要为了形式硬画表；但必须让读者快速知道每篇论文在整体问题中的位置。

总览部分建议交代：每篇论文盯住的核心问题、方法抓手、最关键图片、最强实验和你对它的总体判断。随后用 2-4 句话说明：

- 哪些论文在解决同一层问题？
- 哪些论文看似相近，其实假设不同？
- 哪篇论文是整个拼图里的关键转折点？为什么？

随后优先给出一张总流程图或管线图，说明这些论文如何共同构成一条分析链。**不可使用 Mermaid 语法**，只能使用 Markdown 文本流程图、箭头链路、缩进管线图或文字化管线。如果流程关系本身很简单，可以用一句箭头链路替代，例如：`共同卡点 → 三种解法 → 各自代价 → 总洞见`。

### 三、逐篇拆开时，要让每篇论文都服务于总论点

每篇论文都必须单独成节。先写出这一节的“方法抓手 → 最强证据 → 代价或保留意见”，再把其中最关键的一点压缩成小节标题。小节标题必须是你提炼出的具体判断句，不能只写论文名，也不能照抄“这一篇带来的思考”“实验解剖”这类固定模板。

每篇论文的小节建议覆盖以下信息。不要机械使用这些模块名当标题；可以把它们自然编织成一个引人入胜的讲解段落。

#### 1. 先说明它补上了总问题的哪块拼图
先用一句话总结这篇文章针对什么问题，它核心方法是什么。
用 2-4 句话说明：

- 它试图修补总问题中的哪一个缺口？
- 它的核心假设是什么？
- 它和其他论文相比，切入角度有什么不同？

#### 2. 用流程图或短链路讲清楚它怎么做

优先给出一个简短流程图或管线图。可以使用箭头链路、分层管线、要点列表或短段说明，只要能让读者快速看懂“输入是什么、核心模块是什么、训练或推理策略是什么、输出如何变化”。

如果方法复杂，也必须使用 Markdown 文本流程图、管线图或表格化流程图；不可使用 Mermaid。

#### 3. 关键插图：每篇论文至少贴一张图并分析

必须从该论文原笔记中选择至少 1 张最关键图片。优先级：

1. 方法架构图。
2. 机制流程图。
3. 关键实验结果图。
4. 失败案例或可视化图。

图片格式必须保留为 Markdown 图片：

```markdown
**图：你的解读标题**
![图注或原始 caption](图片链接)
```

图片后必须写 3-6 句分析，告诉读者：

- 这张图应该先看哪里。
- 图中哪些模块对应论文的核心假设。
- 这张图如何支撑总论点。
- 它有没有暴露出复杂度、依赖条件或潜在风险。

如果某篇笔记没有任何图片，必须明确写：

> 原笔记中没有可用图片，因此这一节只能基于文字机制分析；这会削弱该论文在图解层面的可验证性。

#### 4. 实验解剖要让读者看懂它到底证明了什么

优先使用 Markdown 表格、要点清单或短链路总结该论文最关键的实验或消融。如果实验关系很简单，或原笔记没有足够数字，不要硬凑表格；可以使用“实验目的 → 关键现象 → 我的判断 → 还缺什么”的讲法。无论采用哪种形式，都要写 2-4 句点评：

- 哪个结果最有说服力？
- 哪个结果可能受数据、指标、baseline 或评估协议影响？
- 它对总论点贡献了什么证据？

如果原笔记缺少实验数字或表格，必须说明“笔记中没有足够实验细节”，并用文字或要点说清楚论文声称了什么、笔记里有哪些证据、可信度如何、还缺什么。

#### 5. 最后给出这一篇在全局里的价值和疑点

可以用短表格总结，也可以用 3-5 条要点总结。重点说清楚：你相信的部分、你保留意见的部分、它给其他论文补上的拼图、它留下的新问题。

这部分要有判断，不要只重复作者结论。

### 四、横向对照：只讲会改变结论的碰撞

这一节不是“方法差异 / 证据强弱 / 张力”三张清单，也不是把每组论文逐一过一遍。先在内部完成这些比较，再只把**会改变读者对路线选择、结果可信度或部署边界的少数碰撞**写出来。不要把这三个内部分析步骤原样当作 5.1、5.2、5.3 之类的输出标题。

#### 先找真正的分歧，不要把主题相近误写成冲突

一个值得展开的跨论文冲突必须同时满足至少两项：

- 两篇或两组论文在同一目标、任务或指标上给出不同结论，或采用了相互排斥的前提。
- 分歧能追溯到具体的训练信号、数据条件、评估协议、系统约束或失败案例。
- 搞清这件事会改变“该相信哪个结果、该选哪条路线、还缺哪项验证”中的至少一项。

仅仅是方法不同、指标不同，或“都还有局限”，不算冲突。若评测协议、数据规模或任务定义不一致，先明确它们**不能直接比较**，而不是把不同数字硬写成谁打脸谁。

#### 用 2–4 个短论证替代一整页盘点

- 优先写 2–4 个最有杠杆的碰撞；若笔记里只有一个真的成立，宁可只写一个，也不要凑到六个“张力”。
- 每个碰撞用一个由具体事实反推的标题，不能叫“张力 1”“性能 vs 成本”“真正值得讨论的是”。例如标题应当说清“哪项证据在什么条件下失效”或“哪个假设让两条路线分叉”。
- 每个碰撞最多由两个短段组成：先写 `A 的前提/证据 → B 在何处不成立或付出什么代价`；再写 `这会怎样改变判断`。第二段给带条件的结论，不要另起一段重复“判断：”。
- 只引用支撑当前冲突的 1–3 个关键数字、图或失败案例。不要在同一段塞入所有论文名、benchmark 和指标；其余证据留在逐篇分析里。

#### 证据强弱只服务于裁决，不做总账

只有当读者需要快速看清“哪项结论暂时可信、哪项仍未决”时，才插入一张很小的证据表（3–5 行）。每行必须对应前面某个碰撞，并写清证据为何足够或不足；禁止把所有论文、所有主张、所有 benchmark 罗列成一张总账表。

方法路线图也同理：只有当它揭示了一个隐藏的前提分叉时才画。可用一条短链路表示，例如：`共同目标 → 不同前提 → 结果不应直接横比 → 需要补的验证`。不能据此臆造论文之间存在“接力”“替代”或上下游关系。

#### 保持研究讨论的语气

把结论落在证据边界上，而不是写成辩论赛判词。避免“打脸”“掀桌”“刷分”“纯端到端的浪漫时代”“必然成为标配”等媒体化或预言式措辞。没有原笔记支持时，不要预测具体年份、产业采用、监管走向或论文尚未验证的混合方案。

### 五、最后回到总论点，收束成一个真正的判断

最后必须回到整体判断。

必须包含：

1. 一段总洞见：这些论文合起来最重要的启发是什么。
2. 一个“如果只记住一张图/一个表”的提醒：指出文章中哪张图或表最关键。
3. 一个“我对这个方向的判断”：趋势、风险、下一阶段可能的瓶颈。
4. 一句话结论：用一句短句概括整篇文章。

## 风格要求

- 全文使用中文，除非用户明确要求英文。
- 像算法专家给同行讲自己的阅读判断：直接、短句、有判断，但不故作煽动，也不写媒体化或论文腔标题。
- 优先使用 Markdown 文本流程图、管线图、表格和图片，少写连续长段；但不适合结构化表达的地方，可以用“结论句 + 证据句”的短段文字讲清楚；不可使用 Mermaid。
- 除开篇小剧场外，每个连续正文段只承载一个结论，通常 2–3 句、35–75 个汉字，最多 90 个汉字；超过上限必须拆分或结构化。
- 每个核心章节优先使用一种结构化表达：表格、流程图、图片、因果链或要点列表；不要为了形式牺牲清晰度。
- 标题必须是原创判断句、引导句或总结句，且必须由该节最终内容反推出来；不能照抄本 Prompt 的标题，也不能使用“这一篇带来的思考”这类模板化标题。
- 可以批判，但批判必须有推理和依据。
- 不要写油腻套话，例如“具有重要意义”“未来工作广阔”。

## 图片与图表使用原则

- 每篇论文至少使用 1 张原笔记中的图片。
- 每张图片前要有一句“看图提示”。
- 每张图片后要有 3-6 句分析。
- 如果原笔记中有 Table，要尽量保留核心数字；可以转成 Markdown 表格，也可以用文字解释关键差距。
- 如果图片链接失效或缺失，要明确说明，不要假装已经看到了图。
- 除原论文图片外，文章优先额外包含至少 1 个总流程图或管线图，且不可使用 Mermaid。
- 横向比较优先用短论证；只有 3–5 个结论确实需要并列裁决时才使用小表格，不能用总账式大表代替分析。

- 禁止逐篇摘要堆叠。
- 禁止只做相关工作综述，不做洞见判断。
- 禁止编造原笔记中没有的数字、图片、作者背景或实验结论。
- 禁止遗漏任何一篇输入论文。
- 禁止把某篇论文只放进总览表而不单独分析。
- 禁止省略每篇论文的图片分析。
- 禁止使用 Mermaid 语法画图。
- 禁止照抄本 Prompt 的固定标题。
- 禁止为了满足格式而硬凑表格；表格、流程图和图片都要服务于讲清楚问题。
- 禁止把“方法差异 / 证据强弱 / 跨论文张力”照搬成横向章节的固定小标题，或逐条罗列每篇论文的共同点和局限。
- 禁止把协议、数据或任务不一致的结果硬做胜负比较；必须先说明不可比的条件。

- 禁止写行动规划类章节。
````

## 可选模式
